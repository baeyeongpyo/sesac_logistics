# MentorPi 물류 창고 및 파렛트 관리 설계

## 1. 목표

참고 이미지의 물류센터 배치를 Gazebo Sim Harmonic 월드로 재구성하고,
기존 포크리프트형 MentorPi M1 차량 2대가 실제로 운반할 수 있는 파렛트
시스템을 추가한다.

월드 시작 시 FRESH 파렛트 3개와 NORMAL 파렛트 3개를 적재 상태로
배치한다. 실행 중에는 Gazebo 네이티브 CLI를 통해 파렛트를 생성, 삭제,
적재 또는 공파렛트 상태로 전환하고 현재 목록을 조회할 수 있어야 한다.

## 2. 범위

### 포함

- MentorPi 차량 `robot_1`, `robot_2` 2대
- 참고 이미지와 유사한 창고 구역 및 동선
- FRESH 및 NORMAL 작업 구역
- PICO 입출고 구역과 파렛트 적재 존
- 충전 구역, 도로, 작업장 번호 및 바닥 표식
- 컨베이어, 로봇팔, 충전기의 정적 외형과 충돌체
- 실제 질량, 관성, 마찰 및 포크 채널을 가진 동적 파렛트
- 파렛트에 고정되는 FRESH/NORMAL 적재 상자
- 정지 상태에서의 `loaded`와 `empty` 상태 전환
- Gazebo Transport 기반 CLI 생성, 삭제, 전환 및 목록 조회
- 기존 ROS 2 차량 제어와 센서 브리지 유지

### 제외

- 컨베이어, 로봇팔 및 충전기 구동
- 상자 낱개 단위의 물리 시뮬레이션
- 이동 중인 파렛트의 상태 전환
- ROS 2가 반드시 필요한 파렛트 관리 API
- 자율 물류 작업 스케줄러와 경로 계획 로직

## 3. 설계 원칙

1. 파렛트 본체는 상태 전환 시 제거하지 않는다.
2. 적재 상태는 별도 화물 모델의 생성, 결합, 분리 및 제거로 표현한다.
3. Gazebo 물리 엔티티 변경은 시뮬레이션 업데이트 단계에서만 수행한다.
4. 정적 설비는 단순 충돌체를 사용하여 라이다와 경로 계획을 안정적으로
   지원한다.
5. 바닥 표식은 시각 요소로만 구성하여 차량 물리에 영향을 주지 않는다.
6. 파렛트 관리 기능은 Gazebo Transport만으로 동작해야 한다.

## 4. 전체 아키텍처

### 4.1 `WarehousePalletManager`

`WarehousePalletManager`는 월드에 로드되는 Gazebo Sim C++ 시스템
플러그인이다. 다음 책임을 가진다.

- 기본 파렛트 6개 생성
- 런타임 파렛트 생성 및 삭제
- 파렛트 ID, 종류, 상태 및 엔티티 레지스트리 유지
- 파렛트 정지 여부 검사
- 적재물 생성 및 제거
- 적재물 결합 및 분리 요청
- Gazebo Transport 서비스 제공
- 처리 결과와 오류 메시지 반환

Transport 콜백은 물리 엔티티를 직접 변경하지 않는다. 콜백은 명령을
스레드 안전 큐에 넣고 결과를 기다린다. 플러그인은 `PreUpdate`에서
명령을 순서대로 적용하고 성공 또는 실패 결과를 콜백에 전달한다.

### 4.2 동적 파렛트와 적재물

파렛트 본체와 적재물은 서로 다른 동적 모델이다.

- 파렛트 모델은 상판, 받침 및 포크 채널을 포함한다.
- 적재물 모델은 여러 상자가 쌓인 외형을 가지지만 하나의 강체다.
- FRESH 적재물은 녹색 식별 요소를 사용한다.
- NORMAL 적재물은 파란색 식별 요소를 사용한다.
- 적재물은 Gazebo Sim의 `DetachableJoint`로 파렛트에 고정한다.
- `empty` 전환 시 조인트를 분리한 뒤 적재물 모델을 제거한다.
- `loaded` 전환 시 적재물 모델을 생성하고 조인트 결합이 확인된 후에만
  상태를 확정한다.

이 구조는 상태 전환 중에도 파렛트 본체의 위치와 포크 접촉 상태를
유지한다.

### 4.3 정적 창고 모델

창고 설비는 시각 형상과 단순화한 충돌 형상을 분리한다.

- 컨베이어: 벨트, 프레임 및 가드 외형과 하나 이상의 박스 충돌체
- 로봇팔: 베이스, 링크 및 그리퍼 외형과 단순 실린더/박스 충돌체
- 충전기: 본체, 케이블 영역 및 충전 바닥 구역
- 적재 랙: 프레임과 정적 배경 상자
- 벽과 안전 펜스: 라이다에 보이는 고정 충돌체
- 바닥 표식: FRESH, NORMAL, PICO, 도로 2, 작업장 1~4, 충전 및
  진입/대기 기호

## 5. 물리 규격

### 5.1 파렛트

파렛트 외형의 전체 경계 치수는 다음 값을 정확히 사용한다.

| 항목 | 값 |
|---|---:|
| 길이 | 0.135 m |
| 폭 | 0.135 m |
| 높이 | 0.030 m |
| 포크 채널 중심 | y = ±0.050 m |
| 포크 채널 수직 구간 | z = 0.008~0.024 m |
| 포크 채널 유효 높이 | 0.016 m |
| 목표 질량 | 0.12 kg |

상판, 받침 및 채널 형상은 전체 경계 치수를 넘지 않아야 한다. 충돌체는
실제 포크가 통과할 수 있도록 채널 부분을 막지 않는다.

### 5.2 MentorPi 포크 정합

기존 포크 규격은 길이 0.180 m, 폭 0.014 m, 두께 0.010 m이고 중심
간격은 0.100 m다. 30 mm 높이의 파렛트에 삽입할 수 있도록 좌우 포크
링크 중심의 초기 높이를 약 25 mm에서 18 mm로 낮춘다.

- 포크 두께와 길이는 변경하지 않는다.
- 포크 중심 간격은 변경하지 않는다.
- 승강 조인트의 0.110 m 이동 범위는 유지한다.
- SDF와 URDF의 포크 위치를 같은 값으로 유지한다.
- 파렛트 채널과 포크 사이에는 수직 및 수평 여유를 둔다.

### 5.3 적재물

| 항목 | 값 |
|---|---:|
| 최대 바닥 크기 | 0.125 × 0.125 m |
| 목표 질량 | 0.25 kg |
| 물리 단위 | 하나의 강체 |
| 종류 | `fresh`, `normal` |

적재 상자는 복수 상자처럼 보이도록 여러 시각 형상을 사용하되 물리
충돌체 수는 제한한다.

## 6. 월드 배치

기존 `mentorpi_warehouse` 월드 이름과 약 10 × 8 m의 작업 경계를
유지한다. 참고 이미지의 상단을 +Y, 우측을 +X로 해석한다.

- 좌측: 컨베이어, 작업장 1~4, 정적 로봇팔 2대
- 중앙: FRESH 구역과 기본 FRESH 파렛트 3개
- 상단 중앙: PICO 입출고 구역과 파렛트 적재 존
- 우측 상단: NORMAL 구역과 기본 NORMAL 파렛트 3개
- 우측 중앙: 충전기와 충전 바닥 구역
- 하단 우측: 도로 2, 대기/출차 표식, 차량 시작 구역
- 하단 좌측: 회차와 접근을 위한 개방 공간

기본 파렛트는 모두 `loaded` 상태로 시작하고 차량이 남쪽 접근면에서
포크를 삽입할 수 있도록 서로 간격을 둔다.

차량 시작 위치는 파렛트 및 고정 설비와 겹치지 않도록 하단 도로 구역에
배치한다.

초기 동적 엔티티의 기준 배치는 다음과 같다. 파렛트 모델의 기준 높이는
바닥면인 z = 0.0이다.

| ID | 종류 | 상태 | X | Y | Yaw |
|---|---|---|---:|---:|---:|
| `pallet_01` | fresh | loaded | -1.0 | 0.6 | 0.0 |
| `pallet_02` | fresh | loaded | -0.5 | 0.6 | 0.0 |
| `pallet_03` | fresh | loaded | 0.0 | 0.6 | 0.0 |
| `pallet_04` | normal | loaded | 2.9 | 2.4 | 0.0 |
| `pallet_05` | normal | loaded | 3.4 | 2.4 | 0.0 |
| `pallet_06` | normal | loaded | 3.9 | 2.4 | 0.0 |
| `robot_1` | - | - | 1.8 | -2.8 | 1.5708 |
| `robot_2` | - | - | 3.2 | -2.8 | 1.5708 |

CLI로 생성할 수 있는 파렛트 원점은 X = -4.5~4.5 m,
Y = -3.5~3.5 m 범위로 제한한다.

좌표 옵션이 없는 CLI 생성 요청은 하단 좌측의 전용 스폰 위치
X = -2.5 m, Y = -2.8 m, Yaw = 0.0 rad를 사용한다. 이 위치가 파렛트나
차량으로 점유된 경우에는 겹쳐 생성하지 않고 `SPAWN_POSE_OCCUPIED`
오류를 반환한다.

## 7. 상태 모델

각 파렛트는 다음 정보를 가진다.

- ID
- 종류: `fresh` 또는 `normal`
- 상태: `empty`, `loading`, `loaded`, `unloading`
- 파렛트 모델 엔티티
- 파렛트 기준 링크 엔티티
- 적재물 모델 엔티티
- 조인트 연결 상태

정상 전이는 다음과 같다.

```text
empty -> loading -> loaded
loaded -> unloading -> empty
```

명령 처리에 실패하면 안정 상태인 `empty` 또는 `loaded`로 되돌리고,
중간 상태를 외부의 최종 상태로 보고하지 않는다.

## 8. 정지 판정

상태 전환은 다음 조건을 모두 만족할 때만 허용한다.

- 파렛트 선속도 ≤ 0.02 m/s
- 파렛트 각속도 ≤ 0.05 rad/s

기준값을 초과하면 상태 전환을 거부한다. 같은 최종 상태와 같은 종류를
요청하면 엔티티를 변경하지 않고 성공으로 응답한다. `loaded` 상태에서
다른 종류를 요청하면 기존 적재물을 안전하게 제거한 뒤 새 종류를
적재한다.

파렛트 삭제 역시 물리 상태 손상을 피하기 위해 정지 상태에서만
허용한다.

## 9. Gazebo Transport 및 CLI

플러그인은 Gazebo 표준 메시지를 사용하는
`/warehouse/pallet/command` Transport 서비스를 노출한다.

- 요청 형식: `gz.msgs.StringMsg`
- 응답 형식: `gz.msgs.StringMsg`
- 서비스 제한 시간: 5초

요청의 `data` 필드는 다음 파이프 구분 문법을 사용한다.

```text
spawn|ID|KIND|STATE|X|Y|YAW
state|ID|STATE|KIND
remove|ID
list
```

`state` 명령에서 `STATE=empty`이면 `KIND`는 빈 문자열일 수 있으며 기존
종류 메타데이터를 유지한다. `STATE=loaded`이면 `KIND`를 반드시 지정한다.

응답의 `data` 필드는 다음 중 하나다.

```text
ok|COMMAND|DETAIL
error|ERROR_CODE|DETAIL
```

사용자용 `palletctl`은 이 서비스 요청 문자열을 구성하고 응답을 사람이
읽을 수 있는 형태로 출력한다.

`run.sh`는 실행 중인 `gazebo-server` 컨테이너에서 `palletctl`을 호출하는
명령을 제공한다.

```bash
./run.sh pallet-spawn pallet_07 fresh loaded
./run.sh pallet-spawn pallet_08 normal empty --x 1.4 --y 2.0 --yaw 0.0
./run.sh pallet-state pallet_07 empty
./run.sh pallet-state pallet_07 loaded normal
./run.sh pallet-remove pallet_08
./run.sh pallet-list
```

명령 형식은 다음과 같다.

```text
pallet-spawn ID KIND STATE [--x X --y Y] [--yaw YAW]
pallet-state ID STATE [KIND]
pallet-remove ID
pallet-list
```

위치 옵션을 생략하면 X = -2.5 m, Y = -2.8 m, Yaw = 0.0 rad를 사용한다.
`--x`와 `--y`는 항상 함께 지정해야 한다. 좌표를 지정하고 `--yaw`만
생략하면 Yaw = 0.0 rad를 사용한다. Transport 요청에는 `palletctl`이
결정한 최종 X, Y, Yaw 값이 항상 포함된다.

ROS 2는 이 관리 경로의 필수 의존성이 아니다. 기존 MentorPi 속도, 포크,
센서 및 TF 브리지는 현재 ROS 2 구성을 유지한다.

## 10. 입력 검증과 오류 처리

- ID는 `^[a-z][a-z0-9_]{0,31}$` 규칙을 따른다.
- 종류는 `fresh` 또는 `normal`만 허용한다.
- 상태는 `loaded` 또는 `empty`만 허용한다.
- 중복 ID 생성은 거부한다.
- 등록되지 않은 ID의 상태 전환 및 삭제는 거부한다.
- 월드 작업 경계를 벗어난 생성 좌표는 거부한다.
- 기본 또는 지정 생성 위치가 기존 파렛트나 차량과 겹치면 생성을
  거부한다.
- `--x`와 `--y` 중 하나만 지정하면 CLI 입력 오류로 거부한다.
- 이동 중 상태 전환 및 삭제는 거부한다.
- 적재물 생성, 조인트 결합, 분리 또는 제거가 시간 제한 안에 끝나지
  않으면 실패로 처리한다.
- 실패 응답은 파렛트 ID, 요청 작업 및 원인을 포함한다.
- 부분 실패 시 가능한 범위에서 기존 안정 상태를 복구한다.

## 11. 파일 경계

구현은 다음 책임 단위로 분리한다.

- `worlds/warehouse.sdf`: 월드 플러그인 설정과 구역 배치
- `models/warehouse_*`: 정적 창고 설비 모델
- `models/pallet/`: 파렛트와 FRESH/NORMAL 적재물 SDF
- `plugins/warehouse_pallet_manager.*`: 명령 큐, 레지스트리 및 상태 머신
- `scripts/palletctl`: Gazebo Transport CLI 래퍼
- `run.sh`: 컨테이너 실행 명령 진입점
- `test/`: SDF 계약, 명령 파싱, 상태 머신 및 통합 테스트

플러그인 공유 라이브러리는 패키지의 `lib` 경로에 설치하고
`GZ_SIM_SYSTEM_PLUGIN_PATH`에서 탐색 가능하게 한다. 모델 경로는
`GZ_SIM_RESOURCE_PATH`에 패키지의 모델 디렉터리를 추가한다.

## 12. 검증 전략

### 12.1 정적 계약 테스트

- 파렛트 전체 치수가 0.135 × 0.135 × 0.030 m인지 검사
- 포크 채널이 좌우 포크 형상과 겹치지 않는지 검사
- URDF와 SDF 포크 높이가 일치하는지 검사
- 기본 파렛트가 FRESH 3개, NORMAL 3개인지 검사
- 차량 수가 정확히 2대인지 검사
- 정적 설비에 구동 플러그인이 없는지 검사
- 기존 Harmonic 명명과 브리지 계약이 유지되는지 검사

### 12.2 플러그인 단위 테스트

- 명령 파싱
- ID, 종류, 상태 및 좌표 검증
- 기본 위치 적용과 지정 위치 우선순위
- `--x`/`--y` 쌍 검증과 점유 위치 거부
- 중복 및 누락 ID 처리
- 상태 전이와 동일 상태 재요청
- 정지 임계값 판정
- 실패 시 안정 상태 복구

### 12.3 Headless 통합 테스트

1. 월드 시작 후 기본 6개를 조회한다.
2. 좌표 없이 일곱 번째 파렛트를 생성하고 기본 위치를 확인한다.
3. 점유된 기본 위치에 추가 생성을 요청해 거부되는지 확인한다.
4. 지정 좌표로 여덟 번째 파렛트를 생성한다.
5. 파렛트를 `empty`로 전환한다.
6. NORMAL 적재 상태로 전환한다.
7. 추가 파렛트를 삭제한다.
8. 목록과 Gazebo 엔티티 상태가 일치하는지 검사한다.

### 12.4 물리 검증

- 포크가 파렛트 채널에 충돌 없이 진입하는지 확인
- 포크 상승 시 파렛트가 함께 상승하는지 확인
- 적재 상태에서 화물이 파렛트와 함께 유지되는지 확인
- 공파렛트 전환 후 파렛트 본체 위치가 유지되는지 확인
- 차량 주행 중 파렛트가 과도하게 미끄러지거나 전복되지 않는지 확인

### 12.5 회귀 검증

- `mentorpi_gz_sim` 테스트
- `mentorpi_description` 모델 테스트
- Docker 번들 테스트
- 전체 빌드와 headless healthcheck
- 기존 센서, TF, 포크 명령 및 SLAM 계약

## 13. 완료 기준

- 참고 이미지의 주요 구역과 설비를 월드에서 구분할 수 있다.
- 차량은 정확히 2대다.
- 기본 파렛트는 FRESH 3개와 NORMAL 3개다.
- 파렛트 외형 경계는 정확히 135 × 135 × 30 mm다.
- 두 차량의 포크가 파렛트를 실제로 들어 올릴 수 있다.
- 정지 상태에서 적재/공파렛트 전환이 가능하다.
- 파렛트 본체는 상태 전환 중 제거되지 않는다.
- Gazebo 네이티브 CLI로 추가, 삭제, 상태 전환 및 조회가 가능하다.
- 파렛트 관리는 ROS 2 없이 동작한다.
- 기존 MentorPi 차량 및 센서 회귀 테스트가 통과한다.
